# F and P: Empirical Record

**Status.** A developmental record of the empirical application of the F/P workflow, begun on 22 November 2026 and kept in parity with the code. Its base is `boundary_board_states_f_p_construction.md` (§1, items 73 and 74), which this file does not change. It adds no primitive to the primitive catalog and does not touch the hard core. It is stated in general terms: no piece, material, position or engine is part of it. It does not accumulate attempts. It records what the development of the code makes understood, and in particular what is not willing to be baked into the code, including as a comment. The code was first written on 22 November 2026. The designer's statements on the goal front, the exact check and what P takes as input are in `boundary_board_states_f_p_exact_check_goal.md` and `boundary_board_states_f_p_goals_general.md`, which are later than this file.

**Consolidated on 24 November 2026.** Restatements of the exact check goal file were removed, and duplicated lists were merged. No code was changed.

## 1. The designer's statements

1. **The record is developmental.** What matters is the developmental progress made in creating the empirical application of what the construction file specifies, so it is understood what is not willing to be baked into the code, including as a comment (construction file, item 74).
2. **The shape of the code.** There are two functions, F and P. Each takes two engine parameters and two priors, or leaves the priors empty if there are none (construction file, item 74). Their contents are the programmable goal front and are left open. The integration of the priors and the engines, as the foundational basis, is what proceeds empirically from there (item 74).
3. **What is integrated now, and what is not.** The loop can start from P with a batch or from F, and a determined schematic would be a mistake to hard code. Recording engine settings with a batch is not integrated, because anything optional added to a batch or to the priors scales storage. Such properties can be a separate optional file, and only the vital information is held with the priors. Marking engine moves as heuristic or certified is not integrated and is left to the goal front, since it belongs to an approach that deviates from the proof tree approach and is not a constraint at the lowest level of the architecture. Measuring storage and time per cycle can wait (22 November 2026).
4. **The entry.** An entry holds d, and no move is added. The metric of what d holds is what matters, and d is not one quantity (construction file, item 79). Certification follows from the d-depth limit and from the proof tree once the operation is completed and what to keep is resolved, so a separate certified distinction should not exist. Whether an entry has resolved is shown by whether it carries the index, and an entry at the outer bound of a tree carries d alone. Nothing means not resolved, a d of 1 is the boundary of the proof tree for instance, and a number with the information about the terminal status is certified at the limit (construction file, items 80, 81 and 87). The source field and the engine name are garbage that accumulates. Symmetry is not held in an entry: the notation is a redundant storage requirement, one entry covers the folds of its position, and a transformation that lands in another segment gives the same priors for both segments (construction file, items 85 and 86). The index points to board states, and the legend is superseded: it points to the last board state that precedes the terminal condition that moves the irreversible segmented boundary, or to the terminal condition within the segment, as segmented dependency board state locations, with no legend to fetch (exact check goal file, statement 8). (An earlier statement that the move held at an entry is variable, chosen from the viable pool of moves that satisfy the certification, is superseded by this one.) (22 and 23 November 2026.)
5. **The shape of the engine slot is fixed by the compatibility constraint, and the use of an engine's answers is left to the goal.** The slot is fixed only by what compatibility requires: an engine that runs locally and speaks UCI, evaluates a position to a limit, and reports the depth it reached. Further capabilities, such as several lines or leaving moves out, are optional, declared by the engine, and can be removed if they ever affect storage at scale. How an engine's answers are used is left to the goal (23 November 2026).
6. **The anchor of a self-play is any board state.** The anchor need not be the initial position, a game is a path between board states from chosen anchors, and the work runs from the most terminally understood root (exact check goal file, statement 1). The code carries a start for the whole batch only.
7. **P takes a batch of board states and merges nothing, and the current code requires change.** The goal for P should take a batch of board states and not a batch of games, and P should not merge anything. The code for P integrates a specification and excludes architectural variance that is meant to be open to programming, which requires change immediately (exact check goal file, statement 9; 23 November 2026). Not changed yet.

The statements on the d field and its perimeter, the first test, and the engine's deviation from a proof tree are in the exact check goal file, statements 2 to 4.

## 2. What the code fixes

The code is in `code/` beside this file, as a package of seven parts. Each line gives what the code fixes and where it comes from.

1. **Two functions with the same plumbing.** F takes an engine and a set of priors for each side and a goal for each side, and gives a batch. P takes a set of priors for each side, a batch, the two engines and a goal, and gives a set of priors for each side (engine integration, item 20; construction file, items 74 and 75).
2. **The goal is a parameter that is the body.** For F the goal is an object whose hooks, a move hook and a done hook, are both optional. For P the goal is the function called with the context, which returns the new priors. A goal is loaded from stored code by path (construction file, items 76 and 77).
3. **The engine slot.** An engine has a name, settings, and a method that gives a move with an optional score and depth. An engine result carries no certificate. An engine may declare optional capabilities (several lines, leaving moves out), a goal can ask whether an engine supports one, and they can be removed as a unit (§1, item 5). The UCI wrapper declares both and the two test engines declare none.
4. **The priors container.** The priors are held in segments, one for each irreversible segmented boundary. A function gives the segment of a position, and it is a parameter. Its default is the key the documents give: material, with bishops told apart by the colour of their squares, pawn structure and castling rights (construction file, item 83 and reading 72). This is about irreversible segmented boundaries and not about the outer bound of a proof tree or a boundary board state (construction file, item 82). An entry holds d, always present, and the index, present only where the position resolved to a destination, so an entry with d alone marks the outer bound of a proof tree. The index is an opaque value held as given, and its type is not decided (§1, item 4). No symmetry condition is held. The key of a position is a function that can be replaced, and the default is the position text without clocks.
5. **The loop.** F, then P, then F on the priors P gave (engine integration, item 20). It starts with P when a batch is given and with F when none is (construction file, item 13). The order after the start is not claimed to be fixed, and the loop is a convenience around the two functions, which can each be called alone. A batch can be built from a list of moves, with each move checked as legal, or read from a PGN file or text, with a start position taken from its header where there is one.
6. **What F supplies and what a goal supplies.** F supplies the board, the legal moves, the end of a game, and the batch with duplicate games dropped. A goal supplies the choice of move and when the batch is complete, so the number of games is a goal input (construction file, items 24 and 36). Both sets of priors are given to every goal, so visibility is the goal's choice (item 6).
7. **What P builds from a batch (as the code is, and to be changed).** P merges the board states of the lines of the batch by position into one structure, with the moves played between them, the places where lines begin and end, and how many lines pass through each state, and gives it to the goal with the batch. This is working data for one call and is not stored with the priors. It is what §1, item 7 says requires change, and `structure.py` is to be left unused (exact check goal file, statement 12).
8. **The shape of what P gives back.** P requires a pair of priors, one for each side, and refuses anything else. Every entry must have a d, a whole number of zero or more, and an entry with no d is refused, because what cannot be certified is not added (construction file, items 2, 4, 28, 43 and 81). The check is of shape only and does not judge what a goal keeps or omits.

**Baseline choices made by the code.** Each stands in for an open item and is not an answer to it.

- When a goal leaves the move to the default, the engine chooses, and the priors are not consulted. How a goal uses them is the open item on the query surface (construction file, §3).
- Duplicate games are dropped within a batch only and not against the priors. A game ends at the rules' end of game with a draw claim, or at a cap on plies that is a parameter.
- The baseline P adds nothing, since no check has resolved anything and an entry with no d is not added (construction file, item 81). It replaces the baseline P that kept every line.
- The batch is a list of games, each a start, a list of moves and a result. This stands in for the open item on the batch format, and is what §1, item 7 changes.

## 3. What is kept out of the code

1. **The exact check.** Nothing in the framework performs a check. A check is what a goal for P supplies.
2. **A keep or omit rule.** None beyond the baseline.
3. **A unit for the window.** There is none, so nothing counts against a window.
4. **A boundary definition.** The key of a position is replaceable, and no boundary is computed.
5. **Any filtering of priors by side.** Both sets are always given to a goal.
6. **A fixed number of games.** Held only by a goal that supplies it.
7. **A hosted fetch of goals and a layout for storing the priors.** Goals are loaded from a local path, and the container is held in memory and not written to disk.
8. **Anything optional recorded with a batch or an entry.** This covers engine settings with a batch, a record of where an entry came from, and the limit of the proof size apart from d (construction file, item 2 has it for each boundary, so where it is held waits on the boundary key). Anything optional scales storage (§1, item 3).
9. **A heuristic or certified mark, a certified field, and a move per entry.** The first is left to the goal front, and the second is the presence of d (§1, items 3 and 4).
10. **Measurement of storage and time, and of how an engine's moves deviate from a proof tree.** Not added (§1, item 3; exact check goal file, statement 3).
11. **The legend, and transformations by symmetry.** The index is an opaque value, and a goal for P that resolves a position supplies it. An entry holds no symmetry condition. The folds within a segment and the equivalence between segments are a property of the key and are not implemented (construction file, items 81, 85 and 86, readings 72 and 75).
12. **A search to rederive a line, and a check for the pool of equals across a change of scope.** The code has no search of its own. Whether a rederivation goes by d, by the condition or by both, and whether the pool check is a recurring clean-up, a function of P, or P with a goal, are left open (construction file, items 88 and 89).
13. **A use of an engine's score or depth.** The default move takes the engine's move and nothing else, and anything further is the goal's (§1, item 5).
14. **A list or index of the positions at d of 1, and a record of what has been attempted.** Not held. The d field and the region it encloses show them (exact check goal file, statement 4).

## 4. Readings

1. **Divergence came from the engine's state, and the code does not provide it.** This file's reading of a run with a UCI engine at fixed settings, offered for correction. The games of one batch did not repeat, so no game was dropped as a duplicate. This is read as an effect of state the engine carries between games and not as a means of divergence the code gives. Engine integration, reading 20, leaves the means unspecified, and the code leaves it to the goal. If an engine is run with no carried state, repeated games would be expected, and this has not been run.
