# Chess Endgame Perfect-Play Workflow — Full Reference

Covers the complete pipeline from constructing a material's full landscape through analyzing it for multi-perfect-play findings. Current scope: **Black restricted to a bare king** (KXvK / KXYZ...vK, up to five non-king White pieces). This document is the reference to use until the multi-piece-Black refactor lands — see `loser_count_and_multipiece_black_refactor.md` for that separate track, which this document's §7 now links into directly.

---

## 0. One-time setup

Build the solver once per material-family variant you need. All variants come from the same source file.

```bash
# Single-attacker engines (only needed if working with these specific, older, single-piece tools)
g++ -std=c++17 -O2 -o kqvk_solver compositional_trajectory_solver_modular.cpp
g++ -std=c++17 -O2 -DPIECE_ROOK -o krvk_solver compositional_trajectory_solver_modular.cpp
g++ -std=c++17 -O2 -DPIECE_PAWN -o kpvk_solver compositional_trajectory_solver_modular.cpp

# General/multi-piece engine -- this is the one the rest of this document uses
g++ -std=c++17 -O2 -DPIECE_GENERAL -o general_solver compositional_trajectory_solver_modular.cpp
```

`general_solver` handles any White material combination — one king plus **up to five** other pieces (at most one pawn) — against a bare Black king. That's **7 total pieces on the board**, matching Syzygy's own tablebase convention, and the ceiling is a real bit-budget limit of the packed-state representation, not an arbitrary round number (see §5). Use it for everything below unless you specifically need one of the older single-piece tools.

Materials with **0-2** non-king White pieces are the most battle-tested (KQvK, KRvK, KBNvK, KBBvK have all been run end-to-end and cross-checked). **3-5** non-king pieces are supported by every tool in this pipeline and have been directly tested for correctness, but expect the reachable position graph to be dramatically larger — there's no disk-backed storage yet, so a genuinely large material may hit real memory limits regardless of how carefully it's swept. Test with a small `--max-nodes` cap before committing to a full run on anything past 2 pieces.

## 1. Full workflow for a new material (e.g. KBNvK)

### Step 1 — Generate the exhaustive seed list

```bash
python3 generate_exhaustive_positions.py --white B,N --out material_seeds.txt
```

- `--white` — comma-separated White piece letters, e.g. `Q`, `R`, `B,N`, `Q,P`, or any combination of up to 5 (e.g. `Q,R,B,N,P`).
- True combinatorial enumeration: every legal placement of every piece is tried, not just one placement per king pairing — for one non-king piece this is ~370-500K seeds; for two, ~24-30 million; for 3+, expect it to keep growing steeply (see §0's caution on scale).
- Each seed is checked for legality, including that Black's king isn't already attacked by a White piece before White's first move (a real bug this project found and fixed — see §6).

**If the material includes a bishop and no pawn, run this twice — once per bishop color, into the same database:**

```bash
python3 generate_exhaustive_positions.py --white B,N --out material_light.txt --bishop-color light
python3 generate_exhaustive_positions.py --white B,N --out material_dark.txt --bishop-color dark
```

A bishop's square color is conserved by every legal move — light-squared and dark-squared bishop positions are genuinely disconnected components of the state graph, proven directly (zero overlap across millions of explored positions). For **two** bishops, there are **three** distinct, disconnected cases, not two: `--bishop-color opposite` (one of each — the practically common configuration), or `light`/`dark` (a same-colored pair, requiring an underpromotion to reach in a real game).

**Running without `--bishop-color` at all is also a legitimate, deliberate choice now**, not just an oversight to catch — confirmed directly: discovery correctly finds each color's full component regardless of what other seeds share the file, and `--max-nodes` protects memory identically either way, since what's capped is discovered node count, not seed count. The tradeoff is practical, not correctness: an unsplit seed file for a two-piece material is roughly 24.5 million lines, taking ~14s and ~1.5GB just to load into the sweep script, versus doing two smaller, explicit passes. Either approach is safe; pick based on whether you want that load cost paid once (combined) or twice (split).

If the material has a pawn, no extra flag is needed — the generator automatically places it on rank 2 for forward-reachability. At most one pawn is supported.

**A pawn alongside a bishop breaks the clean light/dark disjointness the split above depends on.** The invariant only holds because a *non-promoting* bishop's square color is conserved by every move it makes — but a pawn can promote to a bishop, and a promoted bishop's color depends on which file it lands on, independent of the original bishop's color. So a "light" seed can, via promotion, reach a position with the original bishop on light and a newly-promoted one on dark — exactly the kind of position the split was never designed to reason about for a single bishop. This isn't a correctness risk: `discover()` seals already-known positions regardless of which sweep found them first, so any overlap between the "light" and "dark" runs just means the second one correctly recognizes some positions as already-proven rather than re-discovering them. It does mean the two runs for a bishop+pawn material likely aren't as cleanly disjoint as the naming suggests, so don't be surprised if the second half's discovery count looks smaller than a bishop-only material's would.

### Step 2 — Run the sweep

```bash
python3 run_full_sweep.py material_light.txt --db material_perfect_play.db --solver ./general_solver --fresh
python3 run_full_sweep.py material_dark.txt --db material_perfect_play.db --solver ./general_solver
```

(Omit `--bishop-color` entirely and just run once if the material has no bishop, or if you've deliberately chosen the combined, unsplit approach above.)

**This script was rewritten during this project and now works differently than earlier versions — if a command you've used before stops being recognized (e.g. `--batch-size` errors as unrecognized), you're looking at stale documentation or a stale copy of the file, not a bug.** What changed and why:

- The seed file is fed to the solver in large, **contiguous chunks** (default 200,000 lines, `--chunk-size` to change it) — known and unknown seeds mixed together freely. There's no separate Python-side pruning pass anymore; the C++ solver's own `discover()` seals already-known positions internally, in compiled code, far faster than a Python scan ever did.
- This exists because the actual dominant cost at scale wasn't discovery or classification — it was reload overhead. Measured directly on a real, ~22M-row in-progress KBNvK sweep: the C++ solver's own database reload took 68.1s, and the *old* script's Python-side prune scan added another 33.7s on top, **every single dispatch**, regardless of how little of that dispatch's work was actually new. Collapsing thousands of small dispatches into far fewer large ones is what actually fixes this — diluting a batch with known seeds was never the real problem.
- `--max-nodes` (or auto-detection from system memory if omitted) is the actual, direct memory-safety mechanism, and it's completely independent of chunk size — confirmed empirically by feeding a chunk that mixed known seeds with a seed guaranteed to trigger massive new discovery, capped low, and watching it stop cleanly at exactly the cap regardless of how many other seeds rode along. Raising `--chunk-size` well past the default is safe from a memory standpoint; the only real cost is a bigger one-time seed-file load.
- **Resumability changed too**: since there's no more per-seed prune scan to naturally pick up where a stopped run left off, progress through the seed *file* (not the database) is tracked in `<db>.sweep_progress`, a small JSON sidecar recording how many lines have been fed to the solver so far. Re-running the identical command resumes from that offset directly. If the positions file's name or line count doesn't match what's recorded, resuming is refused with an explicit prompt rather than silently sweeping from the wrong offset.
- `--fresh` only on the **very first** invocation for a database — wipes any existing file (and the `.sweep_progress` sidecar) after an explicit confirmation prompt if real proven positions already exist. Every subsequent invocation (dark half, or resuming after a stop) should **omit** `--fresh`.
- Progress output now reads `CHUNK N (... seed lines, known and unknown mixed) -- through X/TOTAL of the full list (Y%)`, not the older `BATCH N (... genuinely new seeds)` format.

**An older version of this script, using `--batch-size` (default 12) with Python-side pruning, is still functionally correct and safe** — it was used successfully to complete a real KBNvK sweep during this project by scaling `--batch-size` up progressively (1000, then 10000, then 100000), which works because `--max-nodes` protects memory independently of batch size there too. It's simply less efficient at scale, since it pays *two* reload costs per dispatch (its own Python prune-scan plus the C++ solver's reload) rather than the newer script's one. Either script produces an identical, correct database — this is a performance difference, not a correctness one.

**Discovery failing on `--max-nodes` is all-or-nothing for the whole invocation, not per-seed — confirmed directly.** `discover()` runs one shared frontier across every seed fed to it at once; if that combined discovery exceeds the cap, *nothing* from that invocation gets written, including any number of genuinely easy seeds that happened to be bundled alongside one hard one. Tested directly: two trivially-resolvable seeds bundled with one seed engineered to blow the cap produced no database file at all — not a partial one, none. This is the concrete reason batch/chunk size choice matters beyond just efficiency, and it generalizes to every material, not just a specific one:

- A **small** batch/chunk size (down to 1) isolates which specific seeds are genuinely hard, and protects every other seed's progress from being discarded alongside a hard one it happened to share an invocation with. Worth doing at the start of any material without an established track record for how well-behaved its state space is.
- A **large** batch/chunk size is more efficient (far fewer database reloads) but more exposed to this same failure — one hard seed anywhere in a 200,000-line default chunk discards the whole chunk's progress, easy seeds included.
- The practical approach that's worked in this project: start small, and **escalate gradually** (e.g. 1 → 20 → 200 → 2000 → 20000, not straight to a huge number) rather than jumping immediately to a large batch/chunk size on unfamiliar material. The signal to watch for when it's safe to jump larger isn't elapsed time or a round number of steps — it's the "already resolved" fraction of what's been scanned so far climbing consistently high (comfortably 90%+). That's what actually indicates the landscape is well-mapped enough that a big batch is unlikely to contain an undiscovered hard seed. This is exactly the situation that made KBNvK's 13.3%-scanned-but-21.9M-already-found jump straight to `--batch-size 100000` safe — the ratio, not the batch-size history, is what to trust.
- If a large batch/chunk ever does fail, the right recovery is to drop back down, not retry the same size — a failure means something specific in that range is the obstacle, and stepping back down is what lets you actually corner which seeds they are rather than repeatedly discarding the same batch's progress against an unknown cause.
- Materials combining a pawn with another piece are worth treating with extra caution here specifically: this project hit a real OOM testing Bishop+Pawn directly (21M+ nodes before running out), and an even earlier version of the engine was OOM-killed by the same material's state space (noted directly in the C++ source's own comments) — there's no reason to expect this is unique to that one combination, so any pawn-containing material without its own track record is worth the same gradual-escalation caution.

**This can be safely stopped (Ctrl+C) and resumed at any time** by re-running the exact same command (minus `--fresh`) — already-proven work (both wins and confirmed draws) is never redone.

**New: `--preload-from <file>` (repeatable, solver flag, not yet wired into `run_full_sweep.py`) seeds a run with an already-completed, separately-solved *material's* database** — not the same material's own resume file, a genuinely different one. Sound whenever the material being swept can reduce, via capture or promotion, into that other material's position space: e.g. `general_solver --full-dag --positions kbpvk_seeds.txt --db kbpvk_perfect_play.db --fresh --preload-from kqvk_perfect_play.db --preload-from kbnvk_perfect_play.db --preload-from kbqvk_perfect_play.db` (repeat once per reduced material — for KBPvK specifically, that's KQvK, KBvK, KPvK, KBQvK, KBNvK, KNvK, and KBRvK under `--full-promotion`). Every position the sweep's own discovery reaches that's already proven in one of those files is trusted and sealed immediately, never re-expanded — built on the exact same underlying mechanism as same-material resume, just applied across materials instead of across runs of one.

Verified directly, not just argued sound: feeding a single already-solved KQvK position back in as a fresh run's own root, with `--preload-from` pointing at that material's completed database, sealed it immediately and found zero new positions to discover, versus a full 372,064-position rediscovery and 21 classification passes without the flag. Also includes a hard safety check — if two preload sources disagree on a shared position's value, the run refuses with the exact mismatched values shown, rather than silently trusting whichever was loaded last; tested directly with a deliberately corrupted second source, confirmed to trigger correctly. That check can only ever catch a genuine disagreement *between* sources, though — a single, uncontested wrong source has nothing to conflict with and will be accepted; a real, honest limit, not a gap in the check.

**Not yet usable through `run_full_sweep.py`**: checked directly against this project's current sweep wrapper — it builds its solver command explicitly (`--full-dag`, `--positions`, `--db`, optionally `--max-nodes`/`--fresh`) with no passthrough for other flags, so `--preload-from` currently only works via direct `general_solver` invocation (§2 below), not a full, multi-batch sweep. Adding passthrough support to the wrapper is a small, separate task, not done as part of this.

### Step 3 — (Optional but recommended) Validate against Syzygy

```bash
python3 validate_general_syzygy.py material_perfect_play.db --syzygy-dir /path/to/syzygy --sample 20000
```

- Requires **both** `.rtbw` and `.rtbz` files for the material itself, **and** for every material reachable by a single capture (e.g. for KBNvK: also KBvK and KNvK) — DTZ probing structurally requires WDL data at every step, confirmed directly from python-chess's own source.
- A difference of exactly 1 ply between engine and Syzygy is expected and reported separately as "within tolerance" — this is a documented property of DTZ table compression, not a disagreement. Only differences of 2+ plies are flagged as genuine mismatches worth investigating.
- Only checks `Distance`, never move choice — Syzygy has no way to verify this project's tied-move/escape-count logic; that's the actual scope of what this project adds beyond what tablebases already provide.
- Omit `--sample` to check every row (slow on a large database) or use a smaller sample first to catch systemic setup problems quickly before committing to a full run.

### Step 4 — Classify

```bash
python3 general_analyzer.py classify material_perfect_play.db --out-dir material_analysis --max-memory-gb 10
```

- `--min-plies N` — skip positions shorter than this (rarely needed).
- `--max-positions N` — cap how many positions get classified (for a quick partial check).
- `--memo-cache-size N` (default 3000) — bounds the internal reachable-set cache; lower it if memory/swap becomes a problem on a large run, raise it if you have RAM to spare.
- **`--max-memory-gb N`** — new: checks the process's *actual* measured memory (not an estimate) every ~10 seconds, and if it reaches this many GB, checkpoints immediately and exits cleanly (exit code 2) rather than letting the OS start swapping. Re-running the identical command resumes from the checkpoint. Unset by default; worth setting explicitly on anything approaching KBNvK's scale or larger. Handles the real Linux-vs-macOS `ru_maxrss` unit difference (KB vs. bytes) internally, so the number you pass means the same thing on either platform.
- The underlying memory footprint per position was substantially reduced during this project without changing any output: the database's in-memory representation switched from a dict-per-position to a lighter namedtuple (~32% less memory for that structure alone), and classification results now drop fields (`children` always; `tied`/`components` for non-independent categories) that are never actually read back out for those categories — an ~80% reduction on the results list specifically. Both changes were verified to produce byte-for-byte identical output to the prior version on real data; this is a memory optimization, not a behavior change.
- Automatically checkpoints progress every 60 seconds to `<db_path>.classify_checkpoint.pkl`, and resumes from it automatically if the same command is re-run after an interruption. The checkpoint is deleted only after a fully successful run.
- Prints live progress every ~10 seconds (including current memory usage if `--max-memory-gb` is set), and separately warns when a single position has 10+ tied moves (these can legitimately take a while on their own — up to `n` reachable-set searches and `n²/2` pairwise checks for `n` tied moves).
- Produces `material_analysis/independent_findings_deduped.csv` — the input to the next step.

### Step 5 — Families

```bash
python3 general_analyzer.py families material_analysis/independent_findings_deduped.csv --out-dir material_families --render-trees material_perfect_play.db
```

- This is the stage that actually produces the "unique findings" count comparable to this project's earlier established KQvK figures — `classify`'s own count is a different, larger, pre-family-collapse number (see §6).
- `--render-trees DB_PATH` — also renders the full move tree for each family/unique finding, for inspection. This reloads the full database, so it benefits from the same memory optimization described in Step 4.
- `--max-lines N` (default 500) — caps how much tree output gets rendered per finding.
- **`--checkpoint-path FILE`** — new: this stage now checkpoints and resumes automatically too (previously it didn't, and an interruption meant starting over). Defaults to `<findings_csv>.families_checkpoint.pkl` if not given. Checkpointing happens at the granularity of one fully-completed group within a role-sweep, since a single large group's pairwise symmetry check — not a whole role — is where a genuinely slow stretch actually shows up. Just re-run the identical command to resume after an interruption.

### Step 6 — Reduce: finding genuinely irreducible perfect-play structure

```bash
python3 general_analyzer.py reduce material_analysis/independent_findings_deduped.csv material_perfect_play.db --out-dir material_reduction
```

This asks a different question than families' role-sweep, and doesn't depend on families having run at all — it reads classify's output directly. Where families asks "which findings recur under a fixed-role sweep," reduce asks whether a finding's own tied branches are actually as independent as they look, and whether the exhaustive landscape as a whole reduces to a compact catalog of genuinely distinct decisions.

**What this catalog does and doesn't claim, stated precisely because the distinction matters:** it is complete and exact for every position reachable via legal play from this material's own starting configurations — every sub-optimal branch, every promotion outcome, every capture-simplified descendant, not just the optimal-play skeleton. It is not an approximation of that reachability closure; it *is* that closure, deduplicated. It does **not** generalize beyond that closure to an unrelated material, and it does not yet recognize the same relative arrangement of pieces shifted to a different part of the board as the same shape — the symmetry check used to canonicalize a terminal is literal board rotation/reflection (the same 8-fold group used everywhere else in this pipeline), not translation-invariant pattern matching. A genuinely portable catalog of principles — one that would recognize "this is the same kind of situation" in a position never literally searched — is a real, substantial next step past what's built here, not something that falls out automatically.

Two phases, run in sequence by a single invocation:

**Phase 1 — tie-branch reduction** (over classify's tied findings only):
- For every finding's own tied root branches, checks whether ONE consistent transform maps one branch's entire forced continuation onto another's, ply for ply — not just whether they eventually land on the same square configuration. This single test correctly catches three things that look different on the surface: literal downstream convergence, a root position whose own self-symmetry pairs up two of its tied moves, and two branches that never touch again but run in exact mirrored parallel toward two different mates. A genuine match gets collapsed into one branch-group — a real duplicate, safe to discard.
- Separately, checks whether each branch's forced continuation eventually reaches (up to symmetry) *another* finding's own root elsewhere in the same findings file. This is recorded as a subsumption edge, not collapsed away — the root-level tie that led there is still a real, distinct decision even if it isn't the final word; deleting it would erase exactly the thing worth preserving.
- `--max-seconds-per-finding N` (default 60, `0` disables) — a hard, per-finding wall-clock budget enforced via SIGALRM. Cost here is not uniform the way classify's is: a 2-way tie sitting at the front of a 70+-ply forced line can cost far more than a wide tie that resolves in a few plies, and this compounds badly under real memory pressure on a large database. A finding that hits the budget is recorded as genuinely unanalyzed, not silently guessed at — see `skipped_findings.csv`.
- `--retry-skipped SKIPPED_CSV` — re-analyze only the findings listed in a prior run's `skipped_findings.csv`, against the *same* findings_csv they came from. Pairs naturally with a much larger (or disabled) time budget, once a handful of genuinely hard findings aren't also blocking hundreds of thousands of ordinary ones. Results are merged back into the existing `branch_reduction.csv`/`skipped_findings.csv`/`subsumption_edges.csv` — the retried finding(s)' old entries replaced, every other finding left untouched. **Two real, confirmed bugs here, both fixed**: (1) the "Phase 1 already complete, skip and reload" check used to fire regardless of `--retry-skipped`, meaning a retry silently reloaded the exact stale, un-retried results and changed nothing at all — it now never applies in retry mode. (2) An earlier version filtered the findings list down to just the retry set before processing, which broke subsumption-edge detection against every OTHER finding (since the lookup table used for that only ever contained the tiny retry subset) — fixed by keeping the full findings list intact and only restricting *which* findings get processed. Both fixes verified directly: a genuine corrupted-then-retried finding was confirmed to produce output byte-for-byte identical to a completely fresh, uninterrupted run, both `branch_reduction.csv` and `subsumption_edges.csv`. **`--retry-skipped` always skips Phase 2 automatically**, even without also passing `--skip-full-landscape` — Phase 2 depends on nothing from Phase 1 (see below), so a retry has nothing for it to redo.

**Phase 2 — full-landscape shapes, identified by (mate, escape-count), counted only from genuine origins** (over the *entire* database, tied or not):

This section has been rebuilt twice since it was first written, each time after a real, confirmed defect — worth understanding the sequence, since it explains both what the numbers mean and why escape count and origin-filtering are both non-negotiable parts of the definition, not refinements:

- **First version**: canonicalized each position independently (position + its own required move, D4-deduped). Measured and rejected: only removes ordinary 2-to-8-fold board symmetry, barely reducing anything meaningful (KQvK: 345,040 → 43,195, matching plain D4 symmetry almost exactly).
- **Second version**: walked forward from every position to the nearest terminal (mate *or* tie, treated as equivalent stopping points). Wrong on two separate, confirmed counts: (1) a tie is not a terminal — it's where multiple shapes, each still flowing toward its own eventual mate, happen to share a common ancestor; a position can belong to *several* shapes simultaneously if a tie in its future genuinely branches to different eventual mates. (2) Even fixing that, canonicalizing by board position alone drops escape count — and this project's whole definition of perfect play has never been distance alone. Built an explicit check and found 88,410 real cases on KQvK where the identical mate, from the identical position, was reachable via two genuinely different total escape counts (confirmed examples: 21 vs 17 escapes; 24 vs 28). A shape's identity is therefore **(mate, cumulative escape count)**, not the mate alone.
- **Third correction, on top of the second**: even with escape count included, counting every position's own resolved set still over-counts, because escape-remaining decreases every ply along a forced chain — so a single, real, zero-branching 14-ply chain on KQvK reported a *different* escape value at three different points along it (36, then 6, then 0) and was being counted as multiple separate shapes, when it's unambiguously one. Fixed by introducing genuine shape **origins**: a position only starts a new shape if it's a tie (an intersection where multiple shapes meet, not a terminal), or if nothing forces play into it at all (a true starting point, or a sub-optimal deviation from perfect play elsewhere — the same underlying mechanism covers both). Every other position is simply further along an already-established shape, not a new catalog entry.

**Current numbers, all measured on the identical KQvK database**: 46 distinct mates, 264,532 genuine origins out of 345,404 total positions (a striking 76.6% — most of an exhaustively-generated landscape is "fresh starts" with nothing forcing play into them, which is a property of exhaustive generation itself, not a chess insight), and **6,436** distinct (mate, escape-count) shapes once origin-filtering and escape count are both correctly applied. The bulk of the reduction (264,532 → 6,436, ~41x) comes from recognizing many different origins converge on the identical (mate, escape) identity — not from origin-filtering itself, which only trims ~23% on its own.

**What this catalog does and doesn't claim, stated precisely because the distinction matters:** it is complete and exact for every position reachable via legal play from this material's own starting configurations — every sub-optimal branch, every promotion outcome, every capture-simplified descendant. It does **not** generalize beyond that closure to an unrelated material, and it does not recognize the same relative arrangement of pieces shifted to a different part of the board as the same shape — the symmetry check on a mate is literal board rotation/reflection, not translation-invariant pattern matching.

**Implementation, two checkpointed passes in sequence over the same database (a third, separate `summarize_shapes` step existed briefly and was removed — see below for why):**
1. `find_shape_origins` — a single O(n) scan marking which positions have a forced-in parent, then flagging every tie and every position without one as an origin. Also counts, for every position, how many OTHER positions reference it as a child via any move (forced or one of a tie's branches) — not just enough to determine origin status, but a full parent count, needed by the second pass below. Checkpoints to `<db_path>.origin_checkpoint.pkl`.
2. `resolve_reachable_shapes` — the main pass, in increasing distance order (topological, no recursion needed — a position's distance is always strictly greater than any of its children's), building each position's full set of reachable (shape id, escape count) pairs and folding origin-summarization directly into the same loop, returning the finished catalog (`shape_registry`, `shape_counts`, `shape_examples`) itself, not a raw per-position dict for something else to summarize afterward. Checkpoints to `--checkpoint-path-landscape`, default `<db_path>.landscape_checkpoint.pkl`. The sort this pass opens with (positions ordered by distance) has no progress reporting of its own — a real, confirmed gap — so it now prints an explicit before/after message specifically for that step, pointing at Activity Monitor / CPU as the actual working-vs-stuck signal during it, rather than leaving a silent, unexplained pause that reads identically to a genuine hang.

**Origins are cached to disk across invocations — a real, separate fix from either pass' own checkpointing.** `origins` and `parent_counts` used to be rebuilt from scratch by `find_shape_origins` on *every* invocation of `reduce`, even one whose only actual goal was resuming `resolve_reachable_shapes` from its own, already-far-along checkpoint. Confirmed directly to be the dominant cost of a real, measured ~40GB memory peak on a genuine KBPvK-scale run — a peak that had nothing to do with the resolve pass itself. Fixed by caching the completed result to `<db_path>.origins_cache.txt` the first time `find_shape_origins` finishes, and loading it directly on every subsequent invocation instead of recomputing — verified to skip the full scan entirely when the cache is present and valid. Validity is checked with a lightweight (not exhaustive) sanity check: the database's current position count and file mtime must both match what's recorded in the cache; a mismatch on either triggers a warning and a full recompute rather than silently trusting stale data. `--force-rerun-origins` bypasses the cache directly. This cache is independent of, and complements rather than replaces, `find_shape_origins`'s own `origin_checkpoint.pkl` — the checkpoint resumes an *interrupted, in-progress* scan; the cache skips a *completed* one on a later, separate invocation.

**The cache itself was pickle-based at first, and that was a real, separate mistake, not just an implementation detail.** Pickling a structure with tens of millions of entries requires an internal memo table tracking every object by identity, specifically to detect and correctly handle shared references — bookkeeping this data has no use for, since it's flat and has no meaningful shared-reference structure to preserve. That table is itself a genuine multi-gigabyte structure that exists only during the write, for zero benefit, and was confirmed directly to be severe enough to tip a real, live run into swap-thrashing so bad it never recovered on its own and had to be killed. Fixed by replacing the pickle format with a plain, line-oriented text file (`db_len` and `db_mtime` on the header line, then `ORIGINS`/`PARENT_COUNTS` sections, one entry per line) — no memo table, no per-object identity bookkeeping, just origins/parent_counts' own already-necessary memory plus ordinary, bounded file-write buffering. The cache file's own write is atomic (temp file, then renamed into place) for the same reason every other checkpoint in this pipeline is: a crash or kill mid-write must never leave a corrupted file masquerading as a valid one. Loading is defensive on top of that — a genuinely corrupted or truncated cache (confirmed directly by reproducing the exact failure: a real cache file truncated in half, fed to the loader) prints a warning and falls back to a full recompute rather than crashing the run outright.

**`origin_checkpoint.pkl` is deleted later than it used to be, closing a real vulnerability window.** An earlier version deleted it the instant `find_shape_origins` returned successfully — before `resolve_reachable_shapes` (or the origins-cache write above) had even started. A crash anywhere in that gap left nothing to resume the origin scan from, forcing a full, expensive redo even though the scan itself had already genuinely finished. Now deleted only once `shapes.csv` is confirmed written, alongside `landscape_checkpoint.pkl` — confirmed directly with a simulated crash immediately after a real checkpoint save, right as the second pass begins: the origin checkpoint survived and correctly resumed on the next invocation.

**Why summarization got folded into this pass, not left as a separate step, and why this matters at real scale:** an earlier version kept every position's own resolved-shapes entry in memory for the *entire* pass, then summarized only the origin subset afterward. On a real ~58.7M-position KBPvK database this was a genuine, measured problem, not a hypothetical one — the structure was still growing without bound past 15M positions resolved, with checkpoint-save time itself more than doubling between consecutive saves, a direct sign of something that never releases memory, not a slow-but-steady process. The fix isn't simply "free non-origin entries once they're no longer needed" — a real, measured finding on that same database was that 69% of all positions (40,575,106 of 58,782,826) are origins themselves, so capping releases to the non-origin 31% would have left most of the actual problem in place. The real fix: fold summarization into the same loop that computes each position's value, so *every* position — origin or not — becomes freeable via reference counting the instant nothing else could still need it (using the parent counts from pass 1: the moment a child's count hits zero, its entry is deleted immediately, not held for the rest of the run). Measured directly, same data, both ways: the old approach peaked at 445.9 MB of Python memory on KQvK; the reference-counted version peaked at 60.8 MB — a **7.3x reduction** — with identical final results confirmed both ways (46 mates, 6,436 shapes).

`--full-position-map`'s own output (`position_to_shape.csv`) is written the same way now — inline, row by row, as each position is processed — rather than requiring the full per-position dict to still exist at the end to write it from, which would have defeated the memory fix for anyone using that flag.

Both checkpointed passes save every `--checkpoint-every-seconds-landscape` (default 60) and resume automatically. **A checkpointing regression happened once here and was fixed directly**: an earlier version shipped this phase with no checkpointing at all, reasoned from a fast run on a small test database that didn't generalize to real conditions — under genuine memory pressure at real scale this phase can run at a small fraction of that speed for hours, and losing all of it to an interruption is a real cost. Both passes now checkpoint properly, verified with genuine abrupt-kill tests, not just a fresh-run comparison.

Produces `shapes.csv` (ShapeId, MatePosition, MateTurn, EscapeCount, Occurrences, ExamplePosition, ExampleTurn) — one row per genuinely distinct shape. `--full-position-map` additionally writes `position_to_shape.csv`, mapping every position (not just origins) to every shape it belongs to — a position mid-flow still correctly maps to its shape's identity, it just isn't what gets counted in the catalog itself.

`--skip-full-landscape` runs Phase 1 only. Like Phase 1, this phase now has an "already complete, skip and reload" check: if `shapes.csv` exists with no lingering checkpoint from either pass, it's treated as already finished. `--force-rerun-phase1` overrides this.

**Phase 2 depends on nothing from Phase 1 — worth stating explicitly, since it answers a real, recurring question.** Both `find_shape_origins` and `resolve_reachable_shapes` take only the database (plus their own checkpoint state) as input — never `findings`, `results`, or `subsumption_edges`. This means retrying or recomputing any part of Phase 1 (including via `--retry-skipped`, below) never requires rebuilding Phase 2, and Phase 2's output can never be invalidated by anything that happens in Phase 1 — confirmed directly from the function signatures, not assumed. `--retry-skipped` reflects this: it automatically skips the full-landscape scan entirely, even without also passing `--skip-full-landscape` (see below).

**Phase 1's own checkpointing, unchanged by any of the above** (Phase 1 and Phase 2 are independent — see the start of this step): checkpoints after every finding's processing *fully* completes (never mid-finding, never before), on whichever of three triggers fires first:
- 60 seconds elapsed (`--checkpoint-path`, default `<findings_csv>.reduce_checkpoint.pkl`)
- `--checkpoint-every-findings` findings completed since the last save (default 200 — guarantees a predictable cadence even if every single finding finishes just under the time threshold, which the time trigger alone could never catch)
- the finding just completed alone took at least `--slow-finding-checkpoint-seconds` (default 5.0) — securing a hard-won result immediately rather than risking it to a kill shortly afterward

Live progress printing (every ~10s) names the actual finding currently in progress — its position and tie-width — specifically so "is this stuck, or grinding through one genuinely hard item" is answerable from the terminal, not something to guess at from a bare count.

As with classify/families, checkpointing anywhere in `reduce` only helps once the process is far enough along to be inside the relevant loop — it does nothing for an interruption during the initial database load itself, which is paid in full on every single resume regardless of any checkpoint. At real scale (tens of millions of positions), that load alone can be the dominant memory cost — see §5.

**Verifying both phases are genuinely complete, without paying the database-load cost again just to ask.** All of the following are direct file checks, safe to run anytime, no Python invocation needed:
```bash
wc -l material_reduction/skipped_findings.csv       # expect exactly 1 (header only, nothing outstanding)
grep -c TIMED_OUT material_reduction/branch_reduction.csv   # expect 0
wc -l material_reduction/branch_reduction.csv       # expect (finding count) + 1
ls material_analysis/independent_findings_deduped.csv.reduce_checkpoint.pkl \
   material_analysis/independent_findings_deduped.csv.retry_checkpoint.pkl 2>/dev/null   # expect neither to exist
ls material_perfect_play.db.origin_checkpoint.pkl material_perfect_play.db.landscape_checkpoint.pkl 2>/dev/null   # expect neither to exist
```
If `shapes.csv` exists and both Phase 2 checkpoint paths report missing, that's a genuine guarantee of a complete, clean write, not just a likely one — confirmed directly from the code: the checkpoint is only ever deleted *after* `shapes.csv`'s own write block fully completes and closes, so there's no window where a partial write could pass this check.

Rerunning `reduce` itself (the plain command, no `--retry-skipped`) is also a valid way to confirm both phases, and will print `Phase 1 output already exists... loading it back` and `shapes.csv already exists... Skipping.` if both are genuinely done — but it still pays the full database-load cost first just to say so, so the file checks above are the faster way to ask the same question.

**`--trace-shape-graph` — the actual upstream-to-downstream structure behind a shape, as a real graph, not a catalog.** `shapes.csv` gives one example position per shape; `--full-position-map`'s `position_to_shape.csv` gives every position's own shape membership, but as flat rows with no move-by-move connectivity between them. Neither answers "what does this shape's full reachability structure actually look like" — which positions lead into which others, where its branches genuinely diverge, where independent paths genuinely converge. `--trace-shape-graph` answers that directly, writing two new files:

- `shape_graph_nodes.csv` (Position, Turn, IsOrigin, ShapeIds — semicolon-joined, since a node can belong to more than one shape)
- `shape_graph_edges.csv` (Position, Turn, Move, ChildPosition, ChildTurn)

**A first version of this was built, and was wrong in a specific, structural way — worth recording since it's the same kind of defect this section keeps documenting elsewhere.** It traced one flat, linear path per (origin, shape) pair. When two different origins converged onto the same later position — which is common; escape count is a value computed backward from the mate, like distance itself, so convergent positions are *already*, correctly, treated as flowing into the identical shape from that point on — that shared downstream segment got written out twice, redundantly, as if it were two separate things. And a tie's multiple branches were never represented as a first-class graph fact, only discoverable by noticing two traces happened to start at the same position. The underlying computation was never wrong; the output format buried exactly the structure that mattered. Replaced entirely with the current graph export, which explores each position once (memoized) and records genuine, deduplicated nodes and edges: a convergent position appears as exactly one node with multiple incoming edges; a tie appears as one node with multiple outgoing edges.

**Verified directly on real output, both structurally and semantically, not just by construction:**
- Convergence: a real KQvK run found a single position reached by 21 different parent edges, appearing exactly once in `shape_graph_nodes.csv`, not 21 times.
- Divergence: ties correctly produce multiple outgoing edges from one node, with `IsOrigin=True` (a tie is always an origin, by this project's own definition) and multiple `ShapeIds` when its branches lead to genuinely different shapes.
- Edge legality: every edge checked directly against the database's own tied moves on a real run — 0 bad edges out of 170,032 checked.
- Path correctness: random origins walked across every shape they reach, confirmed to terminate at the exact claimed mate every time.

**Checkpoints between origins** (the same granularity Phase 1 checkpoints between findings, for the same reason — a single origin's own recursive exploration is the natural atomic unit of work), via the same atomic-save helper and deleted-only-after-output-is-written pattern used everywhere else in this pipeline. Verified with the same three-part rigor used throughout this project: a fresh run, a genuine abrupt-kill-then-resume (byte-for-byte identical to the uninterrupted run), and a resume from an already-100%-complete checkpoint correctly short-circuiting instead of re-scanning (also byte-for-byte identical, and fast — 1.5s rather than re-walking 264,532 origins).

`--trace-shape-ids ID1,ID2,...` scopes tracing to origins/edges/nodes serving at least one of the listed `ShapeId`s, instead of the entire graph — note this filters by mate identity, not the full (mate, escape) shape, so a common mate can still produce a large graph even scoped to just one or two IDs.

**Not yet safe at KBPvK's scale.** This has only been exercised on KQvK (345K positions). It uses a plain, unbounded memoization dict, not the reference-counted approach `resolve_reachable_shapes` needed before it was safe to run at real scale (see above) — running this against a KBPvK-sized database as-is would need the same kind of memory treatment first, and that hasn't been built.

**`build_shape_index.py` — turns `--trace-shape-graph`'s flat CSV output into an indexed, queryable database, so "which shape is this position in" is a real lookup instead of a linear scan.** A standalone script, separate from `general_analyzer.py`, taking `shape_graph_nodes.csv` and `shape_graph_edges.csv` as input:

```bash
python3 build_shape_index.py material_reduction/shape_graph_nodes.csv \
    material_reduction/shape_graph_edges.csv --out material_shapes.sqlite
```

Builds a normalized SQLite database with three tables — `nodes(position, turn, is_origin)`, `node_shapes(position, turn, shape_id, escape_count)`, `edges(position, turn, move, child_position, child_turn)` — indexed on both `(position, turn)` and `(shape_id, escape_count)` in `node_shapes`, so both query directions (position→shape and shape→membership) are indexed, not just one.

**Measured directly on a real KQvK graph, both query directions, correctness-verified against the source CSVs, not just fast**: position→shape lookups came back ~4,700x faster than a linear CSV scan (168ms/query → 0.04ms/query); shape→full-membership lookups ~4,400x faster (611ms → 0.1ms). The honest cost: the resulting index file is roughly 6.1x larger than its two source CSVs combined (285.8MB vs. 46.5MB in that same test) — real storage traded for a large, measured access-speed gain, not a free win. Re-confirmed live against a person's own independently-generated, uploaded database in normal use, not just the original test build — same result, sub-millisecond lookups on real data.

**Produces `.sqlite-wal` and `.sqlite-shm` alongside the main file** — these are SQLite's own write-ahead-log artifacts from the build (the script enables WAL mode), not required for the database to be valid. If the `.sqlite-wal` file is empty, everything's already fully committed into the main file — confirmed this directly, not assumed — and the other two files can be deleted for a single, self-contained `.sqlite` file if preferred.

**A stale-input gotcha worth knowing about directly, not just as a possibility**: a `shape_graph_nodes.csv` generated before the `--trace-shape-graph` escape-count fix (§6) has `ShapeIds` entries like `36;37` instead of the current, correct `36:74;37:74` — the script now detects this specific format mismatch and raises a clear, actionable error naming the likely cause and the fix (regenerate via `--trace-shape-graph`) rather than a raw Python traceback. This is a real trap that's already been hit in practice, not a hypothetical one guarded against preemptively.

**Only exercised at KQvK's scale (136K-345K nodes depending on scoping) so far.** Whether build time, the index-to-source size ratio, and the query speedup all hold up at real, multi-million-or-larger scale is untested.

**`build_segmented_shape_index.py` — a routing index plus one SQLite file per mate, for a genuinely different access pattern than the monolithic index above serves.** Built and tested directly, not assumed to be a strict improvement: measured on real KQvK data, random access across many different shapes was 3.0x *faster* with the monolithic index (0.026ms/query vs 0.080ms/query — opening a fresh file per query has real overhead a single cached B-tree doesn't pay), but 200 queries confined to one shape were 1.9x *faster* segmented (0.007ms/query vs 0.013ms/query — once a smaller file is open, searching it beats searching the whole shared index). Use this one specifically when the actual access pattern has locality — walking a trajectory, many queries within one shape before moving to the next — not for scattered, random lookups across many shapes, where the original `build_shape_index.py` remains the right tool.

```bash
python3 build_segmented_shape_index.py material_reduction/shape_graph_nodes.csv \
    material_reduction/shape_graph_edges.csv --out-dir material_shapes_segmented \
    --routing material_routing.sqlite --max-open-files 100
```

Segmented by mate (the `--trace-shape-ids` granularity), not the full (mate, escape-count) shape identity — a genuinely correct escape-exact split isn't derivable from `shape_graph_edges.csv` alone, since it carries no escape-count column to determine which exact remaining-budget slice an edge belongs to. A mate's own file bundles every one of its escape-count variants together, not the narrower ~4-10KB single-shape slice measured earlier — still dramatically smaller than the full graph, just coarser than that specific number.

**A real, measured failure mode this tool is specifically built to avoid, not just warn about after the fact**: `--max-open-files` must comfortably exceed the material's actual distinct-mate count, or the bounded connection cache thrashes — confirmed directly on KQvK (46 mates): `--max-open-files 20` dropped throughput to ~200 rows/second (a full run would have taken ~29 minutes for node-loading alone); `--max-open-files 100` (comfortably above 46) processed the same data in under 2 seconds, a measured ~70x difference. The tool now pre-scans the node CSV for the actual distinct-mate count *before* any writing begins, warning immediately (with a 5-second pause to allow stopping) if `--max-open-files` looks too small — and separately warns mid-run if eviction counts start climbing in a way consistent with thrashing regardless, in case the pre-scan's own estimate is somehow wrong.

**A second, separate, genuinely serious bug was caught and fixed here: edges were routed by the FROM position's mates, not the CHILD's — wrong whenever a position belongs to more mates than any single one of its own moves leads toward.** Confirmed directly on real KQvK data before this was trusted: `Q:a1 K:a2 k:b7`'s own `Kb3` move only leads toward 19 of that position's 30 total mates; routing by the FROM position wrote that edge into the other 11 mates' files too, which it has nothing to do with. Since escape count accumulates backward from the mate, a child having mate M in its own reachable set is both necessary and sufficient for that specific edge to genuinely belong to mate M's trajectory — the same criterion the original, monolithic `trace_shape_graph` already used. Fixed by routing on the CHILD's mates instead. Re-verified after the fix, on the corrected totals: exact match on total row counts for both nodes (3,601,748) and edges (3,290,140 — down from the buggy version's inflated 3,715,864, which included the incorrectly-duplicated rows) against the source CSVs; zero mismatches on random sample cross-checks that explicitly test both "is the edge where it should be" and "is it correctly absent from where it shouldn't be."

**Only exercised at KQvK's scale.** Whether pass 2's per-edge routing-index query stays fast at real scale (millions of edges, not hundreds of thousands), and whether a real material's distinct-mate count stays in a range `--max-open-files` can comfortably cover, are both untested past KQvK.

**A genuinely better architecture than this tool's own two-pass, CSV-then-segment approach: writing directly to segmented files during the graph walk itself, memory-bounded from the start.** `--trace-shape-graph-segmented` (a new `general_analyzer.py reduce` flag, not a separate script) does this — combines two real, separate fixes:

1. `node_shape_ids` and `edges` (the monolithic `--trace-shape-graph`'s own in-memory accumulators) never actually needed to hold the whole database's worth of data. The moment `explore(state)` finishes computing a position's shape membership and outgoing edges, that data is complete and correct forever — writing it directly to its mate's own segmented file (via the same `BoundedConnectionCache` pattern as the standalone script above) the instant it's computed eliminates the need for these structures to grow with the whole database at all.
2. `reach_memo` (the recursive `reachable_shapes()` cache) is a separate structure fix (1) does nothing for — still holds every state's entry forever under the original design. Fixed the same way `resolve_reachable_shapes`' own `resolved` dict was fixed earlier in this project: `parent_counts` (already computed by `find_shape_origins`, already available) tracks how many not-yet-processed parents could still need a state's cached value, freeing it the instant that count hits zero. Sound despite this function's different (DFS-from-origins, not distance-ordered) traversal, for a reason worth stating precisely: a specific parent's own `reachable_shapes(parent)` call only ever runs its body once (parent's own memoization guarantees this), and that single run is exactly when it consults each child's cached value — so the decrement happens exactly once per distinct parent regardless of the outer traversal's own order.

**A real, severe bug was caught and fixed while building this, before it ever shipped — worth recording precisely, not just noting a bug existed.** The first version called `in_scope_shape_ids(state)` (computing `reachable_shapes(state)` via its own internal loop, which consults — and reference-count-decrements — every child once) and then, *separately*, called `in_scope_shape_ids(child)` again for each child in `explore()`'s own loop. Both `state` and `explore()` are consulting the same child from the same logical parent, but `parent_counts` only ever recorded one real reference. The first consultation correctly decremented a child to zero and freed it; the second then found it already gone and was forced to recompute that child's *entire* downstream subtree from scratch — confirmed directly to cause a real command timeout during testing, not a hypothetical slowdown. The same bug existed a second time in the main loop's own pre-check of each origin before calling `explore()`. Fixed by having `explore()` itself do the single loop over tied moves, consulting `reachable_shapes()` exactly once per child and deriving both the parent's own value and each child's in-scope status from that one call's result — and by calling `explore(origin)` unconditionally for every origin rather than pre-checking scope separately (sound because escape count accumulates backward: a child can only be in-scope if its direct parent is too, so an out-of-scope origin naturally never recurses into anything, at no extra cost beyond what scoping already required).

**Re-verified after the fix, directly against the standalone script's own (corrected) output — two independently-built results, same data, cross-checked, not just self-consistent**: exact match on all 345,404 positions' shape memberships, exact match on all 412,152 distinct edges.

**Same honest gaps as the standalone script, plus one more specific to this function**: only exercised at KQvK's scale. `visited` is still a plain, unbounded set for the whole run (needed to avoid re-exploring, not re-emitting, a position) — smaller than what it replaced, but not zero. No checkpoint/resume yet — output is written incrementally as the walk proceeds, so a crash doesn't lose everything the CSV-accumulating version's crash would have, but a restart currently re-walks from the first origin rather than resuming partway through.

**`--cluster-mates` — an optional pre-pass that directly shrinks the worst-case file-open requirement `--trace-shape-graph-segmented`'s write pass needs, instead of just sizing `--max-open-files` to cover it.** Grew out of a real design conversation, not a pre-planned feature: the earlier per-origin working-set measurement found the *median* origin only needs a handful of distinct mate files open (6, on real KQvK data), but a real, non-negligible tail (~3% of origins) needs close to the material's *entire* mate count — meaning `--max-open-files` still had to be sized to the full mate count to stay safe against that tail, even though most origins never came close to needing it.

**The fix isn't a bigger cache — it's fewer distinct files for the same information.** Mates that are structurally entangled — an origin needing one almost always needs the other too — get grouped into the same physical file, so one open connection covers both. Confirmed directly, not assumed: two mates on real KQvK data had *identical* coverage sets (every origin reaching one reaches the other, Jaccard similarity 1.000) — obvious candidates to share a file with zero downside. Median pairwise Jaccard across all 1,035 KQvK mate pairs was only 0.148, with many pairs at exactly 0.000 (never co-occurring at all) — real, non-uniform structure, not noise a threshold would be fishing for.

```bash
python3 general_analyzer.py reduce material_analysis/independent_findings_deduped.csv material_perfect_play.db --out-dir material_reduction --trace-shape-graph-segmented --cluster-mates --cluster-jaccard-threshold 0.5 --cluster-max-group-size 10 --max-open-files 100
```

**Why coverage-set overlap specifically, not board geometry or a raw frequency count.** Simple geometric features (king-king distance, corner distance) were already tested earlier in this project and found *not* to cleanly separate shape membership — the five largest shapes all spanned the same range on every feature tried. A raw co-occurrence count was considered and rejected too: it conflates "these two mates are structurally entangled" with "both happen to be individually common," which a proper Jaccard ratio (intersection over union) doesn't.

**Memory-bounded by design, specifically because this project already hit this exact failure shape twice before and wasn't going to hit it a third time**: does not build or retain any mate's full coverage set (a dict of large sets of origin tuples) — that would itself risk becoming the next unbounded-growth problem, the same shape as `find_shape_origins`' `parent_counts` and `resolve_reachable_shapes`' `resolved` dict both needed fixing for. Instead accumulates only two small aggregates while walking — `total_count[mate]` and `pair_count[(mate_a, mate_b)]` — with Jaccard recovered exactly as `shared / (total_a + total_b - shared)`. `pair_count`'s own size is bounded by how many distinct pairs ever *actually* co-occur, not the full M²/2 possible pairs.

**Clustering method: greedy, size-capped agglomeration — not plain transitive union-find, and this is fixing a real, confirmed problem, not a hypothetical one.** Plain union-find at a fixed threshold was tried first on real KQvK data: it found the same real structure, but chained too aggressively — A tightly linked to B, B tightly linked to C, so A and C end up forced together even when Jaccard(A, C) itself is low. This produced one group of 21 mates out of 46 on real data — nearly half the material collapsed into one file, clearly not the intent. Fixed by processing pairs in descending Jaccard order and merging two groups only while the combined size stays at or under `--cluster-max-group-size` — highest-confidence merges happen first, and no single group can balloon past the cap.

**Verified end-to-end on real KQvK data, not just the clustering logic in isolation**: 46 mates clustered into 18 groups at the default threshold; `--max-open-files 20` — which would have thrashed severely unclustered (confirmed earlier: ~200 rows/second at this same value against 46 raw mates) — ran cleanly with room to spare. Total output re-verified against the already-known-correct totals: exact match on both node-shape rows (3,601,748) and edge rows (3,290,140). A 100-sample cross-check confirmed every routed position's *true* mate_id (not the group id) is correctly preserved in its stored row and correctly found within its assigned group's file — grouping only changes which file a row lands in, never what gets recorded in it. A small `mate_groups` table (mate_id → group_id) is written alongside the routing index specifically so a downstream consumer wanting "shape X's data" directly can find the right file without already knowing a position in it.

**A real cost, stated plainly, not downplayed**: this pre-pass walks the same reachable structure the write pass walks again afterward — a genuine, roughly-doubling cost on the walk portion of runtime, paid once per material. Worth it specifically when the unclustered worst case is large enough to risk thrashing or exceed a comfortable file budget — not a default-on optimization, which is why it's opt-in.

**The single most important open question for scaling past KQvK, stated precisely rather than glossed over**: the pre-pass's own per-origin cost is O(k²) in that origin's distinct-mate count k (every pair within one origin's working set costs one counter increment). On KQvK, k stayed concentrated at small values (median 6, only ~3% of origins near the max of 43), which is exactly why this pre-pass stayed cheap there. Whether a larger, more complex material's own per-origin working-set distribution stays similarly concentrated — or commonly reaches much larger k, making this pre-pass's own cost the new bottleneck — is genuinely unverified past KQvK. This is the specific number to watch when running `--cluster-mates` on a new material for the first time.

**Does the tuning need to happen fresh on every material, or does it generalize? Precise answer: the mechanism generalizes; the specific numbers don't, not yet.** `--cluster-jaccard-threshold`, `--cluster-max-group-size`, and `--max-open-files` all depend on a material's own coverage-overlap distribution and mate count, neither knowable in advance. `0.5` is the threshold actually verified end-to-end (the code default matches this, not an untested guess) — a known-good *starting point*, not a claim it's optimal for every material. Genuinely good news, though: guessing wrong here has bounded, detectable consequences, not silent or catastrophic ones. `compute_mate_clusters` prints its own resulting group count (and the timing of the pre-pass walk itself) before the expensive write pass ever starts — a bad threshold shows up immediately as "500 mates → 480 groups" (barely helped) rather than being discovered after a long run. If `--max-open-files` is still too low even after clustering, `BoundedConnectionCache`'s own eviction-count warning fires early (after 500 evictions), not silently for the whole run. Nothing in this pipeline fails quietly on a bad tuning choice.

**What re-tuning actually costs, precisely, not just "cheap" or "expensive": redoing Phase 1 and Phase 2, but not the origin scan.** Once `shapes.csv` exists, re-reaching the `--cluster-mates`/`--trace-shape-graph-segmented` code path with different parameters requires `--force-rerun-phase1` — which, by design, also redoes Phase 1 (tie-branch reduction) and Phase 2's full landscape scan (`resolve_reachable_shapes`), not just the clustering step. That's real, non-trivial cost on a large material. The one genuine saving: the origin scan itself (`find_shape_origins`, the single most expensive full-database pass in this pipeline) stays cached in `<db_path>.origins_cache.pkl` and is reused automatically — `--force-rerun-phase1` does not also force this unless `--force-rerun-origins` is passed separately. There is currently no way to re-run *only* the clustering/trace step without also redoing Phase 1/2 — a real, known gap, not something to build a workaround around by hand.

**Both `--cluster-mates` and `--trace-shape-graph-segmented` now checkpoint and resume, added directly in response to a real, confirmed cost, not built speculatively.** An interrupted, uncheckpointed run at real scale (KBNvK, ~7.4M origins) lost real progress with nothing to resume from — a genuinely large cost at that scale, not a minor inconvenience. Both now checkpoint between origins (never mid-exploration of a single origin's own recursive walk — the same granularity as every other checkpoint in this pipeline) every `--checkpoint-every-seconds-landscape` seconds (shared across the full-landscape scan, the cluster pre-pass, and the segmented write pass — one flag, not three), and resume automatically if their checkpoint file is found.

**A durability detail worth being explicit about, since getting it wrong would silently corrupt a resume rather than just cost time.** `trace_shape_graph_segmented` writes its actual output directly to SQLite files as it goes, not at the end — so a checkpoint here has to guarantee the logical progress marker (`visited`, saved in the checkpoint) never claims a position is done before its row is *actually durable on disk*. Every currently-open per-mate/group connection, plus the routing connection, is explicitly committed (`BoundedConnectionCache.commit_all()`, not just the eventual `close_all()`) immediately before the checkpoint file itself is saved — so the two can never fall out of sync. `routing.sqlite` itself is never deleted or recreated on a resumed run (only on a genuine fresh start), and its existing rows plus the restored `visited` set are what makes resuming produce zero duplicate rows.

**Verified with a genuine abrupt kill, not a graceful shutdown or a code-review-only check — the same rigor every other checkpoint in this project has been held to.** Two separate tests, both against a clean, uninterrupted baseline run on real KQvK data: `SIGKILL` mid-*cluster-pre-pass* (at 176,671/264,532 origins) and, separately, mid-*write-pass* (at 98,268/264,532 origins). Both resumed and completed; both produced output **byte-for-byte identical** to the uninterrupted baseline — 3,601,748 node-shape rows, 412,152 distinct edges, identical `mate_groups` mapping, in both cases. The write-pass test additionally confirmed zero duplicate rows in `routing.sqlite` after resuming, directly verifying the commit-before-checkpoint durability logic actually works, not just that it was written.

## 2. Quick reference — direct solver invocation (no sweep wrapper)

Useful for small materials, quick checks, or a handful of hand-picked seeds rather than the full exhaustive list.

```bash
python3 generate_general_seed_positions.py --white Q --out quick_seeds.txt --num-seeds 8
./general_solver --full-dag --positions quick_seeds.txt --db quick.db --fresh
```

- `generate_general_seed_positions.py` produces a small, deliberately-spread seed set rather than exhaustive king-pair coverage — relies on (verified, but not universally proven) connectivity, so prefer the exhaustive generator for anything you intend to trust as complete.
- Same `--bishop-color {light,dark,opposite}` flag is available here too, with the same three-case caveat for two bishops.
- `./general_solver` flags: `--full-dag` (required), `--positions FILE`, `--db FILE`, `--fresh`, `--max-nodes N`.

**A single seed's forward closure is now rigorously verified to be exactly as correct as the full exhaustive sweep — and one important, honest caveat came with that verification.** Seeded `general_solver` with exactly one hand-picked position (skipping both generators above entirely — just a two-line seed file, header comment plus one position) and compared the result against the full, all-368K-seed exhaustive run: zero missing positions, zero mismatched distances, zero mismatched tied moves, across all 345,404 KQvK positions. This holds for a real, mechanical reason, not by luck: a position's value depends only on its own descendants, never its ancestors, and the forward-reachable set from any seed is closed under taking children by construction — nothing outside it is ever needed to correctly value anything inside it.

**The caveat**: on this test, that single seed's discovery reached the *entire* 372,064-position landscape — identical to the full exhaustive seed list's own count. For KQvK specifically, there does not appear to be a smaller sub-landscape to find from a reasonably central starting position, very plausibly because a queen's mobility means White and Black can reach almost anywhere from almost anywhere under merely legal (not optimal) play. Whether this differs on material with genuine structural disconnection (the bishop-color split is the proven example already in this project) is untested and worth checking before assuming single-seed construction saves real work on any given material — verified-correct and verified-smaller are two different claims, and only the first has been confirmed so far.

## 5. Scale: how far this actually goes

The packed-state representation the C++ engine uses internally has a hard, bit-budget-derived ceiling of **5 non-king White pieces** — confirmed by direct arithmetic (WK + BK + turn = 19 fixed bits, leaving exactly room for 5 more 9-bit piece slots in a 64-bit key, with nothing left over). That's 7 pieces total on the board, matching Syzygy's own convention — not a coincidence so much as two independent designs converging on the same practical bit-packing tradeoff.

That ceiling is about what the *data structure* can represent, not what's practically solvable on a given machine. 0-2 non-king pieces is thoroughly proven territory (KQvK, KRvK, KBNvK, KBBvK all completed and cross-validated). 3+ pieces work correctly through every tool in this pipeline — generation, sweeping, classification — but the reachable position graph grows steeply, and there's no disk-backed storage yet, so a genuinely large 3+ piece material may simply exceed available RAM regardless of how carefully it's swept. Treat anything past 2 pieces as "should work, confirm the scale directly with a bounded test first," not "already proven at this scale."

## 6. Known gotchas — worth remembering

- **`--bishop-color` is easy to forget.** Unlike before, forgetting it is no longer automatically a mistake to catch and rerun — running without it now correctly covers both colors in one pass, verified safe under the same `--max-nodes` memory protection. But it does mean a much larger seed file and load time than splitting deliberately, so know which tradeoff you're choosing rather than getting it by default.
- **`--fresh` will prompt before destroying real progress** (on both the seed-sweep database and, in the current `run_full_sweep.py`, its `.sweep_progress` sidecar too), but only if real content already exists — a genuine first run never prompts.
- **Draws live in a separate `.draws` file**, not the main database — don't be surprised the main `.db` file only ever contains wins.
- **The old exhaustive seed generator had a real, now-fixed bug**: about 16% of seeds could leave Black's king already in check before White's first move (an illegal, unreachable position). Fixed going forward; a database built before the fix may still carry a small number of tainted *seed* rows specifically (never anything discovered downstream from them — proven safe by how move generation works). Syzygy validation will flag these as "invalid board constructions" with a note distinguishing this known cause from a genuinely new problem.
- **The KBNvK "more than 2 disconnected components" question from earlier in this project is effectively resolved** by the move to true combinatorial exhaustive enumeration (§1 Step 1) — that concern came from the older, king-pairs-only seed generator relying on a connectivity assumption; true exhaustive enumeration tries every legal placement directly and doesn't depend on connectivity at all, so it can't miss a component regardless of how many there turn out to be.
- **`classify`'s raw count is not the number comparable to earlier project figures.** The "396" KQvK figure (and its currently-reproduced equivalent) is a post-`families` number. Comparing a `classify`-stage count against it directly is comparing two different pipeline stages. **Open, unresolved discrepancy worth flagging**: a from-scratch KQvK run through this current pipeline reproduces 1524 raw classify-stage findings (matching the previously-established figure exactly) but only 528 unique post-`families` findings, not the previously-reported 659 — confirmed this isn't caused by any change made during this project's memory-optimization work (the prior, unmodified code reproduces the identical 528 on identical input), so the cause is somewhere earlier and hasn't been tracked down yet.
- **Memory on a long `classify` run** — meaningfully reduced by default now (namedtuple positions, stripped unused result fields), and `--max-memory-gb` gives an explicit, measured safety net on top for large materials. `--memo-cache-size` remains available to lower further if still tight.
- **`run_full_sweep.py` changed its interface** (§1 Step 2) — if a command that used to work now errors on `--batch-size`, that's stale documentation or a stale file copy, not a regression. The older interface still works correctly if that's what you have; it's just less efficient at scale.
- **A single hard seed can silently discard an entire batch/chunk's worth of otherwise-easy progress** — confirmed directly, not assumed (§1 Step 2). Start small on any unfamiliar material and escalate batch/chunk size only once the "already resolved" ratio is consistently high, rather than guessing a large size up front.
- **`reduce` used to redo Phase 1 from scratch if interrupted anywhere during Phase 2** — a real, now-fixed bug: its checkpoint was deleted the moment Phase 1 finished, before Phase 1's own output files were written, so an interruption afterward left no record it had ever completed. Fixed directly: `reduce` now checks for Phase 1's already-complete output before doing any work, and loads it back instead of re-running. If a version predating this fix is still in use, an interruption during Phase 2 means Phase 1 silently reruns in full on the next invocation.
- **`reduce`'s Phase 2 has been rebuilt twice, not just tuned once** — see §1 Step 6 for the full sequence. In order: canonicalize-each-position-alone (~8x, mostly recovered plain symmetry) → stop-at-nearest-terminal treating ties and mates as equivalent (wrong: dropped escape count entirely, confirmed via 88,410 real counterexamples on KQvK) → the current version, which requires BOTH escape count as part of a shape's identity AND counts only from genuine origins (ties, or positions nothing forces play into), not every position along a forced chain. Output file went `decision_shapes.csv` → `shapes.csv`, and `shapes.csv`'s own column schema changed again when escape count was added (now includes an `EscapeCount` column). None of the historical shape-count figures from earlier versions of this file are comparable to the current output — if a `shapes.csv` predates the `EscapeCount` column, delete it and any stale `<db_path>.origin_checkpoint.pkl` / `<db_path>.landscape_checkpoint.pkl` before rerunning.
- **A checkpointing regression happened on Phase 2, was caught, and is now fixed** — an earlier version shipped this phase with no checkpointing at all, reasoned from a fast run on a small test database that didn't generalize to real, memory-constrained conditions. Both of Phase 2's passes now checkpoint properly (§1 Step 6), verified with genuine abrupt-kill tests. If a version predating this fix is in use, there is no way to resume this phase after an interruption — upgrade before running it at real scale.
- **The exact same checkpoint-resume off-by-one was found and fixed three separate times** across different functions in this file, worth knowing if extending any of this code further: a checkpoint saved at position K (before K's own work for that position completes) must be resumed with a strictly-less-than comparison, not less-than-or-equal — otherwise position K's own contribution is silently skipped forever on resume. Each occurrence was caught by an abrupt-kill test comparing the full resumed result against a fresh, uninterrupted run — a fresh-run comparison alone was not enough to catch it once out of three times, since simply letting an interrupted run continue past its own checkpoint save masks the bug entirely.
- **`families --render-trees` used to crash outright** — a real, separate, now-fixed bug found while replacing Phase 2: `verify_and_count`, the function producing the "EXHAUSTIVE complete perfect-play paths... verified" line in every rendered tree, was missing its own function definition entirely, sitting as unreachable code after an unrelated function's `return`. Any attempt to render a tree would have hit a `NameError`. Restored and confirmed directly by actually running `--render-trees` and checking the output matches the expected format, not just checking the file parses.
- **New `--preload-from` is a solver flag only, not a sweep-wrapper one** — `run_full_sweep.py` builds its solver command explicitly with no passthrough for extra flags (checked directly, not assumed), so cross-material preloading currently only works via direct `general_solver` invocation, not through a full batch sweep. Don't expect it to be picked up by adding it to a `run_full_sweep.py` command line — it will just be silently absent from what actually gets passed to the solver.
- **`reduce`'s Phase 2 hit a real, measured memory crisis at true KBPvK scale, and was rebuilt again to fix it** — not just tuned. A run on the real ~58.7M-position database showed `resolve_reachable_shapes` still growing without bound past 15M positions resolved, checkpoint-save time more than doubling between consecutive saves. The fix: reference-counted release, folding summarization directly into the main pass so every position (not just the ~31% that aren't shape origins) becomes freeable the instant nothing could still reference it — measured directly, same KQvK data both ways, 445.9 MB peak before vs. 60.8 MB after, a 7.3x reduction, with identical final results. `find_shape_origins` and `resolve_reachable_shapes`'s own signatures changed as part of this (the standalone `summarize_shapes` function was removed entirely, folded into the second pass) — if calling either directly from other code rather than through `reduce`, check the current signatures rather than assuming the old ones still apply.
- **`--retry-skipped` silently did nothing at all for a real stretch, and separately would have destroyed other findings' data if the first bug hadn't been masking it** — both confirmed and fixed. Bug 1: the "Phase 1 already complete, skip and reload" check fired regardless of `--retry-skipped`, meaning a retry command ran to completion, printed a summary, and changed nothing — the exact stale, un-retried results got silently reloaded every time. Bug 2, which bug 1 was accidentally preventing from ever triggering: the findings list used to get filtered down to just the retry subset before processing, which would have both broken subsumption-edge detection against every other finding AND caused the retry's own output-writing code to overwrite `branch_reduction.csv` with only the retried finding's single row, discarding everything else. Both fixed together — retry mode now keeps the full findings list intact (restricting only which findings get processed) and merges results back rather than overwriting. Verified with a real corrupted-then-retried finding: output confirmed byte-for-byte identical to a fresh, uninterrupted run. `--retry-skipped` also always auto-skips Phase 2 now, even without `--skip-full-landscape` — see §1 Step 6 for why that's actually correct (Phase 2 depends on nothing from Phase 1).
- **Recomputing origins on every invocation was a real, measured ~40GB memory driver, and pickle made caching it worse before it made it better** — see §1 Step 6 for the full account. Two lessons worth separating: (1) a value that's expensive to compute but never changes between invocations of the same command against the same data belongs in a cache, not recomputed defensively "just in case" — the actual cost here wasn't `resolve_reachable_shapes` itself, it was silently redoing `find_shape_origins` before ever reaching it. (2) pickle is not a neutral default for a large, flat, non-self-referential structure — its identity-tracking memo table is real, unavoidable overhead for data that has no shared-reference structure to preserve, and was severe enough on its own to tip a real run into unrecoverable swap-thrashing. A plain, line-oriented format fixed it outright.
- **A first version of `--trace-shape-graph` was built, shipped, and then fully replaced after a direct, correct challenge that it didn't represent multi-way ties properly** — worth recording as a real example of the difference between "the underlying computation is correct" and "the output format represents that correctness." The computation (memoized, backward-from-mate reachability) was right from the start; the first artifact just flattened it into redundant, duplicated per-origin paths that buried convergence and divergence instead of exposing them. Rebuilt as a genuine deduplicated graph — see §1 Step 6 for the full verification. Also surfaced a real, instructive Python bug worth knowing about generally: a loop variable named `child_turn` inside the same function silently shadowed the actual `child_turn` function for the *entire* enclosing scope, including code defined earlier in the same function — Python determines a name's scope statically for the whole function body, not from the point of assignment onward, so a name reused as a local anywhere in a function makes every reference to it local throughout, even before that reuse textually occurs.
- **A second, separate bug in the same rebuilt `--trace-shape-graph` was found afterward: its `ShapeIds` column silently dropped escape count, using mate identity alone.** Confirmed directly on real KQvK output before deciding whether this mattered: all 46 mates have more than one distinct escape count (one has 133), so the graph's node/edge labels were merging up to 133 genuinely different (mate, escape-count) shapes under a single `ShapeIds` entry — inconsistent with `shapes.csv`'s own, correct `(ShapeId, EscapeCount)` identity, and with `--full-position-map`'s `position_to_shape.csv`, which had kept both fields correctly from the start. Fixed by changing `ShapeIds` to semicolon-joined `"ShapeId:EscapeCount"` entries, the full identity. Re-verified after the fix: full 345,404/345,404 node coverage preserved, convergence (81,828 nodes) and divergence (52,624 nodes) still hold, zero edges with a missing child — the fix corrected the labeling precision without changing the underlying reachability computation at all.
- **`build_segmented_shape_index.py` routed edges by the wrong position for a real stretch — the FROM position's mates, not the CHILD's.** Wrong whenever a position belongs to more mates than any single one of its own moves leads toward — confirmed directly on real KQvK data: `Q:a1 K:a2 k:b7`'s own `Kb3` move only leads toward 19 of that position's 30 total mates; the buggy version wrote that edge into the other 11 mates' files too, which it has nothing to do with. Since escape count accumulates backward from the mate, a child having mate M in its own reachable set is both necessary and sufficient for an edge to genuinely belong to mate M's trajectory — the same criterion the original, monolithic `trace_shape_graph` already used correctly. Fixed by routing on the child's mates instead. Re-verified on the corrected totals (edges: 3,290,140, down from the buggy version's inflated 3,715,864) with explicit positive *and* negative sample checks — not just "is the edge where it should be" but "is it correctly absent from where it shouldn't be," which the original verification hadn't tested and wouldn't have caught this.
- **A severe, real bug was caught and fixed while building `--trace-shape-graph-segmented`, before it ever shipped — worth recording exactly why, as a general lesson about combining memoization with reference-counted freeing.** The first version called `in_scope_shape_ids(state)` (which computes `reachable_shapes(state)` via its own internal loop, consulting — and reference-count-decrementing — every child once) and then, *separately*, called `in_scope_shape_ids(child)` again for each child in `explore()`'s own loop. Both call sites consult the same child from the same logical parent, but `parent_counts` only ever recorded one real reference — so the first consultation correctly freed a child once its count hit zero, and the second then found it already gone, forcing a full recomputation of that child's entire downstream subtree. This produced a real command timeout during testing, not a projected slowdown. The general lesson: reference-counted freeing is only safe if every consultation of a value is accounted for in the reference count — a value being memoized doesn't protect against this, since the bug is in *how many times something is asked for*, not whether asking twice is individually cheap. Fixed by making `explore()` the single place that ever consults a child, deriving everything else (the parent's own value, the child's in-scope status) from that one call's result. The same bug existed a second time in the main loop's own origin-scope pre-check, fixed by calling `explore(origin)` unconditionally instead (sound because an out-of-scope origin's children are, by the same backward-accumulation logic, never in scope either, so nothing incorrect gets written).
- **`--cluster-jaccard-threshold`'s coded default briefly didn't match the value actually verified end-to-end (0.3 in the flag definition vs. 0.5 in the real KQvK test) — fixed by changing the default, not the documentation, since 0.5 is the one with real evidence behind it.** Worth remembering the general shape of this mistake, not just this one instance: a flag's default value is itself a claim, same as any other number in this project, and deserves the same "was this actually tested, or just typed in" scrutiny given to everything else — a plausible-looking default is not the same as a verified one.
